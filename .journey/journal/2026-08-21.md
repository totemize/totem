## Empty-AP recovery

Replaced the intentionally terminal sticky-AP rule with a conservative idle
retry. A new one-minute systemd timer invokes the existing fallback action in
check-only mode. While `totem-ap` is active, `/usr/sbin/iw dev wlan0 station
dump` is the single source of associated clients: any station (Totem, human
FIPS client, laptop, or phone) preserves the AP. Ten uninterrupted empty
minutes deactivate the AP and restart the existing infrastructure → visible
`!Totem` → AP selection cycle. The idle start is a monotonic `/proc/uptime`
value under `/run`, so wall-clock correction is irrelevant and reboot clears
it. Failed connection, station, or uptime inspection removes the marker and
preserves the AP rather than risking a client disconnect. `iw` is the only new
runtime package; no daemon or TCP/FIPS-specific activity tracker was added.

Local checks passed: 102 deterministic Python tests (including empty start,
station reset, expiry, and inspection-failure behavior), Black, Flake8,
ShellCheck, shell syntax, offline NetworkManager profile parsing, all three
systemd units, direct YAML parsing, Ansible syntax/list-tasks, and diff checks.
The network-only role installed the script, idle oneshot/timer, and `iw` on
exactly totem and motown, then converged both at `changed=0`.

A motown-only empty-AP test shortened the threshold to 60 seconds through a
runtime systemd drop-in. Motown activated `!Totem` at 10:36:39 with no clients;
the timer marked it empty at 10:37:00 and deactivated it at 10:38:10, then the
existing fallback action ran and rehosted at 10:38:38. Further accelerated
checks repeated the same cycle at 10:40:20, 10:42:40, and 10:44:50. It rehosted
because the harness's explicit `nmcli connection down` places NetworkManager's
infrastructure profile under a manual autoconnect block until an explicit
`connection up`; this is a harness property, not fallback selection failure.
The independent restore returned motown to `NOBIOS` at 10:45:55.

A second accelerated run closed that harness gap with a temporary clone of the
same infrastructure profile which was not manually blocked and became eligible
only after `totem-ap` was active. Motown hosted at 11:14:44, marked the empty AP
at 11:15:30, and deactivated it at 11:16:40. NetworkManager auto-activated the
newly eligible infrastructure profile at 11:16:41; the existing fallback
oneshot observed `infrastructure reconnected during grace period` at 11:16:56
and did not rehost. The original profile was then activated and the clone was
deleted. This proves the complete empty AP → infrastructure recovery path, not
only AP recycling.

The associated-client guard then used the same 60-second threshold. Motown
hosted at 10:55:59. Its first empty check started the marker at 10:57:00;
totem joined `totem-peer`, received `10.21.0.46`, and appeared in the kernel
station table as MAC `b8:27:eb:0f:93:5c` with increasing traffic. At 10:58:10
the idle service explicitly logged `AP station connected; resetting idle
timer`. Later checks at 10:59:20, 11:00:30, and 11:01:40 preserved the same AP;
24 workstation scans saw one unchanged BSSID for more than three minutes.
FIPS authenticated the exact identities and the encounter reconciled `Have 0
need 0`. One pre-encounter sync exited 1 while the deliberate infrastructure
link was disappearing; the isolated encounter and restored-LAN rounds both
succeeded immediately afterward.
