# 2026-08-21

## CoC and Wi-Fi Aware extension for the radio substrate

Rebased `feat/device-manager-radio-primitives` onto `origin/master` in its
existing isolated worktree, resolving only the journal/index conflicts and
preserving the current master history. No bench device was contacted,
deployed, restarted, or tested: no device is allocated for this work, so every
hardware completion gate remains explicitly pending.

Added typed LE L2CAP CoC and Wi-Fi Aware/NAN capability blocks. Linux CoC
support requires the Bluetooth seqpacket socket API and the matching
central/peripheral role; NAN discovery requires the PHY's `NAN` interface
mode. NAN data-interface capability is reported separately. The production
driver currently returns `supported: false` for NAN data-path negotiation even
when a bleeding-edge kernel advertises `NAN-data`, because this tree does not
yet contain the userspace NDP negotiation backend. Current-Pi unsupported
behavior is therefore explicit rather than inferred or emulated.

Local review also confirmed that direct nl80211 lifecycle operations require
`CAP_NET_ADMIN`, while `totem.service` intentionally runs as unprivileged user
`totem` with `NoNewPrivileges=true`. The implementation checks the effective
capability and reports NAN discovery unsupported when it is absent. It does
not add ambient capabilities, sudo rules, setuid helpers, or broader Polkit
authority; a future narrow NAN broker would need its own security review.

Implemented bounded, payload-blind LE CoC listeners and connections. Listener
PSMs are assigned by the OS and advertised as a two-byte little-endian value
under the FIPS service UUID. Advertisement failure rolls the socket back, so
the known BlueZ failure cannot leave an undiscoverable manager-owned listener.
Connected descriptors can be sent with `SCM_RIGHTS` to the fixed local
`/run/fips/l2cap-handoff.sock`; the device manager never reads or writes link
payload, and FIPS remains responsible for framing, Noise, identity, routing,
and policy. The receiver side is a required follow-up in FIPS before the handoff
can work end to end.

Implemented the upstream `iw ... nan` discovery lifecycle: create only the
manager-owned `totemnan0` interface, start NAN, install paired bounded
publish/subscribe functions, parse match events, remove functions idempotently,
and delete only that interface after the last session. Caller-provided service
information is opaque and base64url-encoded on the CLI carrier. No trust,
selection, routing, or sync policy was added. The mock models the eventual
`aware_dataN` result with scoped link-local IPv6 and the FIPS UDP port while the
production data-path operation honestly remains unsupported.

Local deterministic verification after the first two commits reached 129
passing unit tests. The NAN slice then expanded the local suite to 135 passing
tests, including descriptor passing, socket/MTU cleanup, BlueZ advertisement
rollback, NAN command rollback, event parsing, stable capability reasons,
scoped IPv6 results, API lifecycle, idempotent teardown, and driver contract
parity. Hardware, Android↔Linux CoC/FIPS transfer, and real NAN data-path tests
were not run.

### NAN identity follow-up extension

A source audit against Myco's pinned Android `AwareRadio` implementation and
upstream `iw` found that Android exchanges identity only after discovery, as a
follow-up payload in the form `<npub>|<port>`. Passive discovery information is
empty. Upstream `iw event` identifies these as `FollowUpReceive` and reports
the local instance ID, peer requester instance ID, peer MAC, and service
information. Its send surface accepts the same tuple through `nan add_func
type followup`.

Extended the policy-free substrate with an explicit follow-up capability and
`POST`/`GET /network/wifi/aware/followups`. Callers supply an existing match
ID and strict-base64 payload; the manager derives the instance IDs, service
name, and destination MAC. The CLI backend accepts only UTF-8 without NUL or
line breaks and enforces NAN's 255-byte bound. Sent and received records are
bounded, evented, and removed with their session. The mock produces a
deterministic received identity response for adapter tests.

Only local mock/unit/API verification was performed. No Totem, Android, or
other physical device was contacted; all real interoperability and teardown
gates remain pending until hardware is explicitly allocated.

The complete Python unit selection passes with 136 tests and five hardware
tests deselected. `cargo check` passes. On this macOS host, the unrelated
`totemd` test `sync::tests::policy_failure_and_timeout_retry` repeatedly
exceeded its two-second test deadline (39 other Rust tests passed); the radio
extension does not modify Rust sources, and the Linux PR check remains the
authoritative Rust gate.

## Myco pairing, native file sharing, and Totem Nearby napplet

The original implementation was created in the isolated `feat/myco-napplet`
worktree from `origin/master` (`93e45fc`) because the primary checkout was
under active development elsewhere. It was subsequently rebased onto the
extended `feat/device-manager-radio-primitives` branch so the native Myco
integration can consume its optional transports without conflating that work
with the separately shareable napplet.

### What shipped

Added `integrations/myco`, a Rust/headless Myco peer using the existing FIPS
TUN and device identity rather than starting another mesh node. The integration
matches Myco's paired-file-sharing commit
`852bcda8cd0ccc2b604588c9b33c98e2523cea5b`: pair URIs and signed kinds
9101/9102/9103, NIP-17/NIP-59 file control, TTL-zero Myco MESH frames,
XChaCha20-Poly1305 packages, NIP-44 wrapped file keys, and content-addressed
encrypted blob reads. It preserves the upstream limits and installable-payload
policy. File control and blob access are Circle-gated by the authenticated
FIPS source address; the operator API is loopback-only.

Added an Ansible role, fleet verification, a systemd unit, and `flash.sh`
support. The service receives `/etc/fips/fips.key` through
`LoadCredential`; it never copies the key or changes its root-only mode. State
is private under `/var/lib/totem-myco`.

Created `napplets/totem-nearby` with the current make/design/build/test napplet
workflow. This is intentionally separate from the native integration: Myco can
carry its single `dist/index.html`, while a NIP-5D runtime supplies the
shell-mediated ContextVM capability used to discover a Totem's advertised MCP
tools and invoke one with explicit JSON arguments. The napplet has no direct
network, browser storage, or key access. `spec/11-myco.md` now records this
boundary so “Myco integration” and “napplet” do not collapse into one thing.

### Live bench proof

Deployed the native integration to totem, metot, and motown. Totem issued an
invite, motown submitted the matching Myco request, and totem explicitly
accepted it; both persistent Circle views then contained the other device.

Two 36-byte plaintext fixtures crossed the live FIPS mesh in opposite
directions. Transfer `7b407ab114729722a762f954f9da37ea` completed from
totem to motown and transfer `7fdd949da0c4c6c853cc35a927e686ea`
completed from motown to totem. Both sender and receiver reported `completed`,
the expected size, and no error; received plaintext was compared byte-for-byte.

The actual napplet artifact then crossed from totem to motown as transfer
`40d142b0202442d58a8ea85bcfba9c5e`. Local and received copies were both
17,449 bytes with SHA-256
`7948ce8bf5cb323a25a498db19f6b81234fb72085bd2b2eeb4d482fae3deed29`.
This proves the napplet is a normal Myco-shareable artifact without treating it
as an nsite or native app package.

No Android Myco handset was attached (`adb devices` was empty), so physical
Android interoperability was not claimed. Compatibility was instead audited
against the pinned upstream source and exercised between two independently
deployed Totem endpoints over the exact wire protocol. A future handset bench
run remains the final hardware-specific check.

  (`arm-unknown-linux-musleabihf`, `aarch64-unknown-linux-musl`) passed.
- Ansible syntax passed. Metot and totem passed the full serial fleet verifier;

- Kehto Paja served the napplet target at `127.0.0.1:5173` through its runtime

Two gotchas cost time. First, FIPS node addresses hash the raw x-only public
key bytes, not the textual npub; the corrected derivation now has exact vectors
for all three bench nodes. Second, `PrivateTmp=true` means a shell's `/tmp` is
not visible to the service. Outbound operator files must be staged in a service-
readable path such as `/home/totem`.

The napplet's live Totem action path still depends on a runtime exposing a
Totem ContextVM/MCP service. Myco only transports the file, and totemd's current
v1 bus remains loopback HTTP/SSE; neither is silently promoted into a napplet
runtime or generic remote-control bridge.

### Dependent radio integration

Rebased this branch onto the extended
`feat/device-manager-radio-primitives` head and retained the native Myco
integration and `totem-nearby` napplet as separate artifacts. The napplet did
not gain radio or device-manager access.

Added a native, loopback-only transport adapter. LE CoC requests go to the
device manager and successful descriptors are handed directly to FIPS. Wi-Fi
Aware discovery advertises `myco.fips.v1`; an established data path is
converted to a numeric-scope IPv6 UDP endpoint and submitted through
`/run/fips/control.sock`. Operator-observed LAN and SoftAP endpoints use the
same FIPS `connect` command. The application
protocol continues to address peers exclusively over `fips0`, so the adapter
does not bypass Noise, duplicate FIPS framing, or turn a radio observation into
trust. Optional-lane failure preserves the prior FIPS-TUN path.

The loopback operator surface covers the full manager-owned lifecycle: Aware
matches, discovery stop, data-path removal, CoC listener create/list/close,
outbound connect, and accepted-connection handoff. The npub attached to a lane
is only a dial hint; FIPS authenticates it with Noise and applies its peer ACL,
while Myco Circle membership remains a separate explicit decision.

Review against pinned Myco source corrected an early local design that would
have treated Aware as a direct HTTP route: upstream instead treats Aware and
LAN/AP as FIPS UDP lanes. Deterministic local tests now cover the line-delimited
FIPS control request, scoped IPv6 conversion and resolver acceptance, Aware
data-path injection, CoC handoff sequencing, and failure cleanup. Twelve Rust
tests and strict Clippy pass. No Totem, Android handset, or other physical
device was contacted or tested for this dependent extension; production NDP,
FIPS CoC receiver, Android follow-up interoperability, and real
transfer/fallback measurements remain pending.

The rebased aggregate also passed 136 Python unit tests with all five hardware
tests deselected, both ARMv6 and aarch64 Rust target checks, the napplet's
strict TypeScript and single-file production build, and Ansible syntax with the
repository roles path. These are local contract checks only, not substitutes
for the pending device and Android gates.

After the parent device-manager branch gained explicit NAN follow-up support,
this dependent branch was rebased again. The native adapter now matches the
pinned Android wire contract: passive service information is empty,
and a bounded one-second loop sends `<own-npub>|<port>` once for every new
match. Received follow-ups are strict-base64 decoded, UTF-8 checked, validated
against the npub bech32 shape and a non-zero port, and cached by match.
Data-path requests can consume that cached identity; the original
explicit npub/port input remains available as a fallback. Session stop aborts
the exchange task and removes its cached announcements and identities.

The new adapter test drives discovery, match, follow-up send, and received
identity decoding through a loopback mock device-manager and verifies the
Android wire bytes. Thirteen Myco Rust tests and strict Clippy pass locally.
No physical device or Android handset was contacted; NDP, CoC/FIPS receiver,
real Android interop, teardown, coexistence, transfer, and fallback gates
remain pending.
