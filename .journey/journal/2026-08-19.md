## FIPS bring-up triage (device: totem)

Error under investigation: `Failed to resolve identity: failed to read
config file /etc/fips/fips.key: Permission denied (os error 13)`.

Findings:

- The daemon (`fips.service`, running as root) was healthy the whole
  time. The error was a *manual* `fips` run as user `totem` — the key
  file is root:root 0600 by design (see
  `references/fips/docs/reference/security.md`). Not a bug; the
  security model working. A manual run would also fail on TUN/UDP-2121
  (root-only, held by the daemon).
- Journal prints local time (WEST, UTC+1); fips log lines are UTC —
  the error stamp looked 40 min before daemon start until corrected.
- Cosmetic upstream issue: the error text says "config file" while
  reading the *key* file (`ConfigError::ReadFile`,
  `src/config/mod.rs:725`).

Fix applied: created `fips` group, added `totem`, restarted daemon →
control socket `/run/fips/control.sock` is root:fips 0770; `fipsctl`
now works unprivileged on both devices. (The codex deploy had skipped
the dpkg postinst `groupadd`.)

Real bug found during the restart: **TUN threads can die silently
shortly after restart** — state latches `degraded`, `fips0` disappears
from the kernel, forwarding counters freeze, nothing logged. Second
restart was clean. Dataplane then verified end-to-end (mesh ping 3/3,
counters moving). Upstream tickets suggested: log runtime child exits
(one-liner in `rx_loop.rs` ChildExited arm), investigate the TUN
restart race, fix the ReadFile error wording.

## Architecture checks: TUN vs native FIPS

Question: drop the TUN adapter for native fips (memory/performance)?

Conclusion — **keep TUN**:

- Native "API" is in-process Rust datagrams (no TCP, no sockets, no
  Go binding). Totem's sync stack (NIP-11, challenge, NIP-77
  websockets) is unmodified TCP — it exists *because* of the TUN
  adapter. Even fips's own nostr-relay example runs over TUN.
- Memory math (measured): fips RSS 41 MB of 426 MB; TUN's share is
  ~1–2 MB (2 threads + 1024-slot channel). The mesh stack itself
  dominates and native mode pays it in full.
- TUN's kernel footprint is confined and verified: one `fd00::/8`
  route, one policy rule, no sysctls, ULA can't collide or leak.
- Real lever if ever needed: `node.leaf_only: true` (config, no
  rebuild) — declined for now, totems should route.

Build target check: current binary is `arm-unknown-linux-musleabihf`
(ARMv6 hard-float, static — matches Pi Zero W). BLE transport is
compile-gated off on musl (`build.rs`, BlueZ/libdbus needs glibc) →
the BLE phase needs `arm-unknown-linux-gnueabihf` (device runs
glibc 2.41, compatible). No BLE needed for the demo (detection =
fips peers → NIP-11 probe → ephemeral challenge), so the musl
binary stays. Correction recorded: fips BLE uses L2CAP CoC MTU 2048
— it *can* carry the full IPv6 adapter; earlier "250-byte BLE"
concern didn't apply to fips.

## Cross-relay nostr testing with nak

Goal: exercise the relays end-to-end — publish, read, cross-relay sync —
with `nak` (source in `references/nak`, built armv6 for the devices).

From the host (nak v0.20.1, over the mesh by `.fips` name):

1. published a tagged kind-1 note to totem's relay — success;
2. read it back — exact event id match;
3. isolation check: metot's relay correctly returned nothing (relays are
   independent);
4. `nak sync` (NIP-77 negentropy) totem→metot;
5. metot now serves the identical event. **Cross-relay replication over
   fips works.**

Device-side: built nak from `references/nak` HEAD as a **static armv6
musl binary** (31 MB) via docker buildx — needed a one-time
`tonistiigi/binfmt --install arm` on the host (no arm/v6 emulation),
and a rebuild with `-extldflags=-static` inside the builder image
(the Dockerfile default produces a dynamic musl binary glibc
Raspbian can't run). Deployed to `/usr/local/bin/nak` on both
devices. On-device round: totem published a note with its own nak,
ran `nak sync` between both relays over the mesh; metot read both
notes from its local relay. No host involved.

Findings on the way:

- **Host fips sessions can drop after device restarts** — devices
  fine, host at 1 peer, mesh pings 100% loss. Fix without root:
  `fipsctl connect <npub> <lan-ip>:2121 udp`, instant recovery.
  (No passwordless sudo on the dev host.)
- nak CLI on devices: relays need literal mesh addresses (no resolver
  wiring); content via `-c`, tag flags as `key=value`, positionals are
  relay URLs only.
- Deployment footgun: an `&&` chain after a command that exits nonzero
  (`nak version` doesn't exist in HEAD) silently skipped the rest —
  metot's binary wasn't installed until noticed.

## Benchmark: nostr ops under load (100 events, totem → metot)

Method: `/proc/<pid>/stat` sampler (12-line shell script, 100–200 ms
interval; utime+stime at CLK_TCK=100 + VmRSS), shell `times` for
children aggregates, DB growth via `du`, delivery verified with
`nak req`/`nak count` after every phase. Payload: 100 × ~280-byte
kind-1 notes (~38 KB), tag-scoped filters.

### A. Publish 100 events (loopback, pooled WS)

| Method | Wall | CPU | Per event |
|---|---|---|---|
| 100 × `nak event` invocations | 681 s | 699 s | **~7 s CPU each** |
| 1 × `nak event`, events piped via stdin | 16.2 s | 8.7 s (nak) + 1.2 s (strfry) | 87 ms + 12 ms |

strfry relay: flat 8.6 MB RSS, DB growth ~1.8 KB/event. One-shot CLI
invocations are ~80× the actual work — nak startup dominates on the
Pi Zero. Never drive nostr ops one-invocation-per-event on these
devices.

### B. Negentropy sync via `nak sync` (NIP-77, over mesh)

17.3 s wall (~2.2 KB/s), nak CPU 8.1 s = **47% of a core**, nak RSS
peak **63 MB** (15% of RAM). strfry: 0.1 s CPU source, 0.5 s CPU
dest, RSS ~8 MB both. Delivery 100/100.

### C. Same sync via `strfry sync --dir=up` (C++ CLI, local DB)

**1.22 s wall, 0.10 s CPU (8%), 5.5 MB RSS.** Receiving relay 0.24 s
CPU. Delivery 100/100.

### B vs C: 14× faster, 80× less CPU, 11× less memory

The gap is architectural: nak is a *third-party* driver — pulls IDs
from both relays, builds two in-memory negentropy trees, diffs,
republishes. strfry's CLI keeps its sync tree **on disk** (BTreeLMDB
over its own DB) and speaks negentropy natively over one connection.

Conclusions:

1. The relay stack is never the bottleneck: strfry ≤ 9 MB RSS,
   ~1.6 s CPU combined for the whole sync.
2. nak is testing tooling only — disqualified for ops.
3. **The totem daemon should orchestrate `strfry sync <peer-url>
   --filter=... --dir=both`** rather than implement negentropy in Go.
   Detection (fips peers → NIP-11 marker) → invoke sync → report.
   Open detail: CLI needs root/strfry perms (`/etc/strfry.conf` +
   `/var/lib/strfry/` are root/strfry-only).
4. At ~31 KB/s effective sync throughput, months of personal notes
   sync in seconds-to-minutes. Mesh isn't the constraint; the driver
   shape is.

Also discovered: `strfry --help` lists a `mesh` app (router / stream /
sync) — same family as our spec's flows; the binary must be invoked
via its musl loader (`/opt/strfry/lib/ld-musl-armhf.so.1
--library-path …`), it's not on PATH by design.

Benchmark methodology gotchas (sampler appends — fresh files per run;
`pkill -f`/`pgrep -f` match the invoking shell's own cmdline — signal
by exact PID; nested ssh quoting mangles JSON — heredoc scripts on
device).

## totemd design session (control plane)

Design phase for the control plane; no totemd code yet. Decisions now in
the spec (new `spec/10-control-plane.md` + edits to 02/04/05/06/07/09):

- **totemd**: single Rust daemon = net code + control plane + web server.
  Runs as root to read `/etc/fips/fips.key` (challenge responder signs with
  the device identity). systemd supervises; totemd supervises only
  `strfry sync` children. Root also settles the earlier open question of
  `strfry sync` privileges (config/DB are root/strfry-only).
- **No relay proxying** (flatness): strfry serves the relay port directly,
  stock. Totem marker rides standard NIP-11 fields: `info.name` MUST start
  with `!Totem` (same string as the SSID — one marker everywhere), and
  `info.self` = device npub. Verified in strfry source: `software` is
  hardcoded (RelayWebsocket.cpp:94); `name`/`self` are pure config — a
  custom field would have forced a fork or a front proxy; standard fields
  need neither. Hint stays a hint; the challenge is the proof.
- **Challenge moved to the web port**: `/totem/challenge` served by totemd,
  kind 27235 + `nonce` tag pinned in 07 (freshness window still TBD);
  rate-limited (each hit is a schnorr sign on ARMv6).
- **Bus**: NIP-5D-shaped messages (`{"type":"totem.status.get","id":...}`)
  over HTTP on a loopback-only bind; pushes via SSE `/bus/events`;
  `totem.*` registry pinned in 07. This is our draft of the IPC projection
  (05): NAP grammar now, napplet machinery (manifests/ACLs/sessions) when
  happlets arrive. Peripherals never parse logs (journald is diagnostics);
  pushes are lossy, consumers reconcile via `totem.status.get`.
- **totemctl** = same binary in client mode, a bus client like any other —
  matches fips/fipsctl muscle memory, and keeps the single-writer rule
  (all kind 3 mutations route through totemd).
- **fips interface**: control socket directly (`/run/fips/control.sock`,
  JSON-lines; not fipsctl), `.fips` resolution via UDP `[::1]:5354`
  (embedder path proven on metot).
- **Owner auth**: NIP-98 against an admin npub allowlist in totemd config
  (defers 09's key-management question).

Repo context: PR #9 reduced this repo to the Python hardware stack
(`src/totem`, FastAPI+WS, `deploy/systemd/totem.service`). Footgun noted:
`totem.service` binds `0.0.0.0:8000` — once the AP is up that exposes
NFC/storage/display ops to guests. It should bind loopback in production;
totemd becomes the only public-facing server and consumes the device
manager's API locally.

Next steps: decide totemd's repo home (own repo vs subdir here — see
journal notes in the session log); scaffold totemd (axum + nostr-sdk,
armv6 musl cross like fips); pin port numbers in 07; negentropy throughput
benchmark with a bigger payload.
