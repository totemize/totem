# 2026-08-22

## Capability-oriented hardware runtime ontology

Created `refactor/hardware-ontology` in a dedicated worktree from PR #22's
exact head, `211f890b222c6108dc63c57e6e18fc64ed8d8d97`, so the proposal includes
the additional radio implementations without touching the user's working tree.
No bench device was allocated or contacted; every fleet measurement below
remains a local result or an explicit future gate.

Expanded the original screen/device-manager concern to the complete Python
hardware subsystem. The accepted planning ontology treats physical models and
SKUs as data (`HardwareFacts` plus optional profiles), behavior as independently
versioned capabilities, concrete implementations as independently installable
driver distributions, and selection as deterministic manifest/fact resolution
with visible match evidence. The hardware runtime owns discovery, binding,
resource leases, lifecycle, supervision, health, and events. `screen` stays a
bounded application context consuming narrow display, power, and health ports;
it is neither a driver nor an alternate device manager.

The public SPI is proposed as an independently versioned `totem-driver-api`.
Plugins register through `totem.hardware.drivers`, provide import-free
manifests, and are not imported into the daemon during cataloging or by default
execution. Existing `totem.api`, `totem.devices`, and `totem.managers` paths,
commands, routes, environment names, and units become migration facades rather
than the canonical hierarchy. Requirements and the first roadmap phase now
cover 33 v1 contracts across ontology, plugin packaging, resolution,
supervision, resources, APIs, and verification.

Driver messages follow the NIP-5D-shaped pattern already used by `totemd`:
JSON-compatible `{type, id, ...}` requests, correlated `<type>.result`
responses with `ok` and structured errors, and typed unsolicited pushes.
Unknown pushes are ignored for forward compatibility; unknown ID-bearing
requests receive correlated errors. Plugin identity is bound to the spawn
session, not trusted from payload fields.

### Spike results

Five approved variants were built under `.planning/spikes/`, with executable
harnesses, adversarial cases, machine-readable results, and research notes:

- **001a/001b process topology:** eight per-binding interpreters versus one
  per-provider interpreter completed the same 1,600-request load and forced
  recovery. Across five paired macOS trials, per-binding used eight processes
  and median summed RSS of 94,768 KiB; per-provider used one and 11,872 KiB.
  Per-binding lost one binding on the injected crash; per-provider lost all
  eight. One process per provider distribution is the provisional scalable
  default, with per-binding as a smaller-blast-radius override. The result is
  PARTIAL until Linux PSS and realistic imports run on Pi-class hardware.
- **002a framed JSON:** a 16-byte versioned prefix, canonical JSON envelope,
  and bounded/checksummed raw attachments passed 25 cases covering real Unix
  sockets, one-byte fragmentation, pipelining, size declarations, malformed
  input, integrity, NIP-5D request/result/push rules, and Totem bus fixtures.
  A 250×122 monochrome frame occupied 4,132 bytes versus 5,240 with inline
  base64, saving 1,108 bytes.
- **002b MessagePack:** native and pure-Python MessagePack passed the identical
  25-case suite. Native encoding reduced the 62-byte control frame to 54 bytes
  and the 4,132-byte display frame to 4,085 bytes. The pure-Python fallback was
  about 2.5–3.7× slower than JSON in paired local decode measurements. Current
  MessagePack requires Python 3.10; the pinned last Python-3.9 release has no
  listed armv6/armv7 wheel. Canonical JSON plus raw attachments is therefore
  the provisional v1 carrier; MessagePack stays a reserved optional codec.
- **003 dual hosts:** in-process and executable-child adapters produced
  identical transcripts for eight functional cases, including attachments,
  pushes, errors, deadlines, and post-timeout work. Containment is necessarily
  asymmetric. An uncooperative in-process timeout left a live thread, marked
  the host contaminated, blocked new work, and made lease release unsafe until
  daemon restart. The process host terminated/replaced its child and continued.
  A sacrificial `os._exit(86)` probe killed the in-process daemon but only the
  isolated driver child. The suite was repeated three additional times with no
  surviving workers. This spike is VALIDATED.

The durable refinement is that “same host contract” means functional envelope
parity, never containment parity. Process isolation remains the default.
In-process execution may be selected globally or per plugin, but is an explicit
acceptance of cooperative cancellation and daemon-wide native failure. A
timed-out live thread keeps its resource leases; the runtime must not start a
replacement owner until controlled daemon restart.
