# 2026-08-20

## E-ink Rev 2.1 compatibility and final render

Resumed the Waveshare 2.13-inch display work after the Pi Zero returned
online. The user supplied decisive control evidence: the same assembled
Pi/HAT/panel refreshes successfully when booted from a Pwnagotchi SD card.
That rules out HAT/FPC seating and panel failure.

Compared Totem's V2 transport with Pwnagotchi's current `waveshare_2`
implementation. Pwnagotchi configures GPIO24/BUSY with an internal pull-down
and does not require observing a BUSY leading edge before accepting a V2
refresh. Totem previously used no pull resistor and made that leading edge a
hard requirement. On this Rev 2.1 HAT, GPIO24 remains electrically floating
at idle (it follows both software pull-up and pull-down) and no leading edge
is visible even though the display itself is known to work.

Changes:

- bias active-high BUSY low, matching Waveshare/Pwnagotchi Raspberry Pi
  transport behavior;
- make the V2/Rev 2.1 update path wait on BUSY if asserted without requiring
  the leading edge;
- keep the controller powered for a four-second fallback refresh window
  before callers may put it to sleep;
- add contract coverage for the pull-down and V2 behavior.

Verification:

- full local suite: 74 passed, 4 hardware-marked tests skipped;
- deployed the changed base and V2 drivers to `/opt/totem`;
- invoked `examples/display_text.py` through
  `DisplayManager(driver_name="waveshare_2in13_v2")` on real SPI with the
  exact payload `hello world\n<3 totem`;
- initialization, framebuffer transfer, protected refresh interval, sleep,
  and cleanup all completed with exit status 0.

Physical visual confirmation of the exact final text is still pending from
the person beside the screen; do not call the display goal complete without
that last observation.

## Correction: physical target and controller identity

The preceding diagnosis was based on the wrong physical unit. The display,
camera view, and PiSugar2 are attached to `metot` (`192.168.8.239`), while the
failed V1/V2/V3/V4 and BUSY-line experiments targeted screenless `totem`
(`192.168.8.136`). The floating GPIO24 readings therefore described an open
Pi header, not a display fault. Do not carry those readings forward as HAT
behavior.

`Rev 2.1` is the HAT PCB revision and does not identify the e-paper controller.
On `metot`, the official Waveshare V4 initialization/frame path immediately
rendered `hello world\n<3 totem`; the user confirmed the result and the camera
recorded it. This identifies the attached controller as V4.

The working setup was then promoted into the repository and deployed from that
source state:

- `DisplayManager` now selects `TOTEM_EINK_DRIVER` when no explicit driver is
  supplied, so the API service uses the same configuration path as direct
  manager callers;
- `deploy/devices/metot.env` pins `waveshare_2in13_v4`, and the corresponding
  boot fragment records persistent SPI0 enablement;
- the Raspberry Pi transport prefers Waveshare's gpiozero-style GPIO backend;
- V4 retains power for a bounded refresh-settle interval before callers may
  sleep or close it;
- speculative V2/Rev-2.1 BUSY conclusions were removed from the source and
  tests.

Verification:

- local suite: 81 tests passed, 4 hardware tests skipped;
- the source-built `totem.service` is active on `metot`, has
  `TOTEM_EINK_DRIVER=waveshare_2in13_v4`, and reports the gpiozero/V4 driver at
  250x122;
- SPI is live at `/dev/spidev0.0` and `dtparam=spi=on` is persisted;
- an API call through `DisplayManager` visibly changed the retained image to
  `MANAGER\nBASELINE` under camera observation;
- a second recorded API call changed it back to
  `hello world\n<3 totem`, proving a fresh manager-driven refresh rather than
  relying on the earlier retained e-ink image.
- hardened V4 refresh handling then observed the panel's real BUSY
  assertion/release (no fallback delay), and a final recorded manager call
  again rendered `hello world\n<3 totem` from the source-built service;
- BUSY confirmation is now an explicit Waveshare 2.13-inch driver capability,
  so hardware smoke tests enforce it without imposing that signal contract on
  unrelated display drivers.
